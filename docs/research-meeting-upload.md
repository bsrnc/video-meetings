# Research: технологическая реализация загрузки файла записи встречи

**Контекст:** @docs/plan-meeting-recording-upload-and-analysis.md, @docs/prd-meeting-recording-upload-and-analysis.md
**Дата:** 2026-08-20
**Скоуп:** только Фаза 1 плана (backend — приём и хранение файла записи). Транскрибация/очереди вне скоупа.

## 1. Текущее состояние стека

Проверено по коду репозитория на момент ресерча:

- `apps/api` — Nest.js 11, Express-платформа (`@nestjs/platform-express@11.2.1`), которая тянет `multer@2.2.0` транзитивно (в `package.json` явной зависимости на multer нет).
- Object storage не подключён — нет ни одного S3 SDK в зависимостях, нет клиента, нет env-переменных под storage.
- `docker-compose.yml` в корне поднимает только Postgres (`postgres:16-alpine`, порт `5434`). Ни очереди (Redis/RabbitMQ), ни S3-совместимого хранилища локально нет.
- `Meeting` в `prisma/schema.prisma` — только `id`, `title`, `createdAt`. Полей под файл записи, статус и ошибку нет — нужна миграция (уже отмечено в плане).
- `main.ts` не настраивает лимиты тела запроса и таймауты сервера — только `ValidationPipe` и `app.enableCors()`.
- Тестовая культура проекта — реальные e2e через Supertest поверх реального Postgres в докере (`test/*.e2e-spec.ts`), моков ORM/БД в проекте нет. Это влияет на выбор архитектуры загрузки (см. раздел 5).
- PRD прямо называет размер файлов: "десятки–сотни МБ до нескольких ГБ" — это определяет, что буферизация файла целиком в памяти Node-процесса неприемлема.

## 2. Ключевое архитектурное решение: куда течёт файл

Два принципиальных варианта.

### Вариант A — Presigned URL (прямая загрузка браузер → storage)

Клиент запрашивает у API presigned PUT-ссылку → API создаёт/обновляет `Meeting` (`status=UPLOADING`) и возвращает ссылку → браузер грузит файл напрямую в S3-совместимое хранилище, минуя API-сервер → клиент сообщает API об завершении (или API сам подтверждает через `HeadObject`) → статус обновляется на `READY`/`ERROR`.

**Плюсы:** файл не проходит через Node-процесс API — нет риска забить память/сеть/CPU бэкенда; естественно масштабируется; это стандартный паттерн у AWS/GCP/Cloudflare для больших файлов.
**Минусы:** два HTTP-запроса вместо одного, что расходится с текущей формулировкой плана ("Endpoint загрузки файла записи ... сохранение в storage" — одним вызовом); e2e-тест сложнее — Supertest не может протестировать сам PUT в S3, тест должен отдельно бить по presigned URL реальным HTTP-клиентом против локального S3-совместимого стенда (MinIO); валидация файла (тип/размер) на bytes-уровне до сохранения возможна только через политику storage (presigned POST + `content-length-range`, `starts-with $Content-Type`) или post-hoc проверку после факта заливки — менее гибко, чем серверная валидация по magic bytes.

### Вариант B — Проксирование через API со стримингом (без буферизации)

Клиент грузит файл одним `multipart/form-data` запросом на API-эндпоинт → Nest принимает поток (не буферизует в память/на диск целиком) и стримит его напрямую в S3-совместимое хранилище через multipart upload → по завершении обновляется `Meeting`.

**Плюсы:** один HTTP-вызов, соответствует текущей формулировке плана; e2e-тест тривиален — `supertest.attach()` как обычно; вся валидация (расширение, MIME по сигнатуре, размер) выполняется на сервере до и во время стриминга, единая точка правды.
**Минусы:** upload держит Node-соединение открытым на всё время передачи (десятки секунд — минуты на медленной сети для ГБ-файлов) — нужно поднять таймауты HTTP-сервера; трафик идёт двойным хопом (клиент→API→storage) — на текущем масштабе (внутренний тул) это не проблема, при росте нагрузки может стать.

### Рекомендация

**Вариант B (стриминг через API) для Фазы 1.** Обоснование:

1. Совпадает с уже написанным и одобренным пользователем текстом плана (один endpoint, синхронная валидация с понятным сообщением об ошибке) — не требует пересогласования скоупа.
2. Вписывается в существующую e2e-культуру проекта (`supertest`, реальная инфраструктура в докере, без моков) без специальной настройки тестового HTTP-клиента для прямых обращений к storage.
3. При условии, что буферизация исключена (см. раздел 3), риск по памяти/OOM снимается — единственный реальный минус варианта B (двойной трафик) не критичен для внутреннего инструмента с редкими одиночными аплоудами.

Presigned URL стоит держать в уме как путь миграции, если объём/частота загрузок вырастут — тогда Фаза 1 endpoint превращается в "issue presigned URL", а не переписывается с нуля (тот же S3 SDK, та же схема `Meeting`).

## 3. Как стримить файл в Nest, не буферизуя целиком

Критичная деталь: `@nestjs/platform-express`'s `FileInterceptor('file')` по умолчанию использует `multer.memoryStorage()` — весь файл целиком попадает в `req.file.buffer` как `Buffer` в RAM. Для файла в несколько ГБ и больше одного параллельного аплоуда это прямой путь к OOM процесса. **Нельзя использовать дефолтный `FileInterceptor` без явной настройки storage engine.**

Варианты без полной буферизации в памяти:

- **`multer.diskStorage()`** — файл пишется во временный файл на диске по мере приёма, затем читается `fs.createReadStream()` и заливается в S3 через `@aws-sdk/lib-storage`. Просто, надёжно, работает "из коробки" с multer. Минусы: двойной I/O (запись на диск + чтение с диска + аплоуд), нужна очистка временных файлов (в том числе при падении процесса — orphaned tmp-файлы), нужно доступное дисковое пространство под размер файла (проблема на контейнерах с ephemeral/маленьким диском).
- **Кастомный multer `StorageEngine`, стримящий напрямую в storage** — `_handleFile(req, file, cb)` получает `file.stream` (readable stream из multer, ещё до записи куда-либо) и пробрасывает его прямо в `@aws-sdk/lib-storage`'s `Upload` (эта абстракция принимает `Readable` как `Body`, сама рвёт поток на part'ы ≥5MB и грузит через S3 multipart upload API, с ретраями и контролем конкурентности). Диск вообще не участвует. Это самый эффективный по ресурсам путь и рекомендуемый для Фазы 1, учитывая, что размер файла заранее неизвестен (multipart parsing идёт потоково) — `Upload` штатно работает с потоками неизвестной длины.

**Рекомендация:** кастомный `StorageEngine` поверх `@aws-sdk/lib-storage`. Диск как временный буфер — приемлемый fallback, если стриминговый storage engine окажется сложнее в реализации, чем стоит на Фазе 1, но чистое решение — прямой стриминг.

Дополнительно нужно поднять в `main.ts`/конфиге HTTP-сервера:

- `multer` `limits.fileSize` — жёсткий предел размера (значение лимита ещё предстоит зафиксировать отдельным решением, PRD пока оставляет его открытым).
- Таймауты Node HTTP-сервера — по умолчанию (Node ≥18) `server.requestTimeout` ≈ 300 000 мс (5 минут) и `headersTimeout` ≈ 60 000 мс — для ГБ-файлов на медленном канале 5 минут можно не уложиться. Нужно явно увеличить/снять через `app.getHttpServer()` в `main.ts` после `NestFactory.create`.
- Если в будущем перед API появится reverse proxy/балансировщик — на нём отдельно нужно поднимать `client_max_body_size`/эквивалент и его собственные таймауты (сейчас в репозитории такого слоя нет, deploy-конфигурация не описана — фиксируем как будущий риск, не блокер Фазы 1).

## 4. Валидация файла

Из плана: "невалидный файл отклоняется с понятным сообщением об ошибке" — тип и размер.

- **Размер** — `multer` `limits.fileSize`; при превышении multer сам обрывает поток и кидает `LIMIT_FILE_SIZE` — нужен `ExceptionFilter`/обработка в контроллере, чтобы вернуть человекочитаемое сообщение, а не голую 500/multer-ошибку.
- **Тип — двухуровневая проверка:**
  1. Дешёвый первый фильтр — `multer` `fileFilter` по заявленному `mimetype`/расширению из multipart-заголовков (отсекает явный мусор до траты трафика на стриминг).
  2. Проверка по сигнатуре файла (magic bytes) на первых байтах потока — заявленный `Content-Type` в multipart можно подделать из клиента, полагаться только на него небезопасно. Библиотека `file-type` (ESM, читает сигнатуру из `Buffer`/начала потока) даёт реальный MIME по содержимому. При несовпадении — оборвать стрим (не докачивать файл до конца, чтобы не тратить трафик/место в storage) и вернуть 400 с понятным сообщением.
- Список допустимых MIME/расширений (video/audio для записи встречи — mp4, webm, mov, mp3, wav, m4a, ogg и т.п.) — отдельная конфигурационная константа; точный список тоже пока открытый вопрос, как и лимит размера (совпадает с "требует определения" из PRD).

## 5. S3-совместимое хранилище: провайдер и локальная инфраструктура

- **SDK:** `@aws-sdk/client-s3` + `@aws-sdk/lib-storage` (для стримингового multipart upload) — официальный, модульный, TypeScript-first AWS SDK v3. Работает с любым S3-совместимым провайдером (не только AWS) через `endpoint` + `forcePathStyle: true` (нужно для большинства non-AWS S3-совместимых сервисов, у которых нет virtual-hosted-style DNS для бакетов). Не использовать `aws-sdk` v2 (legacy, in maintenance).
- **Локальная разработка и e2e:** добавить `minio/minio` в корневой `docker-compose.yml` рядом с `postgres` — тот же паттерн, что уже принят в проекте (реальная зависимость в докере, не мок). Даёт реальный S3 API на `localhost` для dev и e2e-тестов без внешних сетевых вызовов и без счёта от облачного провайдера. Бакет создаётся один раз (init-контейнер с `mc` либо ленивое `CreateBucket` при старте приложения, если бакета нет).
- **Прод-провайдер** — не часть Фазы 1 (в плане не зафиксирован конкретный сервис), но благодаря S3-совместимому SDK выбор (AWS S3, Cloudflare R2, Backblaze B2, DigitalOcean Spaces) — это только смена env-переменных (`endpoint`, ключи, `forcePathStyle`), кода не касается.
- **Приватность бакета:** держать бакет приватным (не public-read). В БД хранить только storage key (например, `meetings/{meetingId}/recording.{ext}`), не публичный URL — если в будущем понадобится отдать файл клиенту (воспроизведение), генерировать presigned GET с коротким TTL через `@aws-sdk/s3-request-presigner`, а не открывать бакет наружу. Фаза 1 такого требования не содержит (плана про воспроизведение записи нет), но такое решение не мешает и стоит дёшево сразу.
- **Ключ объекта** — детерминированный, без случайного суффикса (`meetings/{meetingId}/recording.{ext}`): повторная загрузка (сценарий "невалидный файл → повторить загрузку" из плана) просто перезаписывает объект. Множественные записи на одну встречу вне скоупа PRD.

## 6. Модель данных (Prisma)

Расширение `Meeting` под план (Фаза 1, задача 1):

- `recordingKey: String?` — storage key загруженного файла (не URL).
- `recordingStatus: RecordingStatus @default(UPLOADING)` — enum `UPLOADING | READY | ERROR`, а не голая строка: типобезопасность на уровне Prisma Client, единственный источник правды по допустимым значениям (совпадает с формулировкой плана дословно).
- `recordingError: String?` — сообщение об ошибке для отображения на фронте (Фаза 3).
- Дополнительно стоит рассмотреть `recordingSize: Int?` / `recordingMimeType: String?` — не обязательны по букве плана, но дёшевы и полезны для будущей отладки/лимитов; финальное решение — на усмотрение реализации, не блокер ресерча.

**Важный момент про порядок обновления статуса:** Фаза 3 плана требует, чтобы страница отражала статус `UPLOADING` без ручного обновления, пока файл ещё грузится. Раз Фаза 1 — синхронный HTTP-запрос (вариант B), запись `Meeting.recordingStatus = UPLOADING` должна создаваться/обновляться **в момент начала приёма файла** (до того как стриминг в storage завершится), а не только в конце запроса — иначе `GET /meetings/:id`, вызванный параллельно во время долгой загрузки, не увидит промежуточное состояние и Фаза 3 не будет на чём показывать статус "Загрузка".

## 7. Тестирование (Фаза 1 e2e-требование)

Вариант B позволяет писать e2e-тест в существующем стиле: `supertest.attach('file', buffer/path)` на защищённый `JwtAuthGuard` endpoint, без дополнительной инфраструктуры кроме поднятого локального MinIO. Сценарии из плана прямо покрываются:

- успешная загрузка валидного файла → 201, `Meeting.recordingStatus === 'READY'`, объект реально существует в MinIO (можно доп. проверить `HeadObject`);
- отказ невалидного типа/размера → 400 с понятным сообщением, `Meeting` не помечается `READY`;
- доступ endpoint для любого авторизованного пользователя (как остальные `meetings` роуты) — паттерн уже есть в `test/meetings.e2e-spec.ts`, повторяется 1:1.

Раз в проекте нет практики мокать инфраструктуру (Postgres — реальный в докере), тот же принцип стоит распространить на storage: e2e гоняется против реального MinIO, а не против замоканного `S3Client`. Юнит-тесты (если будут) на fileFilter/валидацию сигнатуры можно и нужно писать без сети.

## 8. Итоговый список зависимостей к добавлению в `apps/api`

- `@aws-sdk/client-s3` — S3-совместимый клиент.
- `@aws-sdk/lib-storage` — стриминговый multipart upload поверх клиента.
- `@aws-sdk/s3-request-presigner` — на будущее (presigned GET/PUT), не строго обязателен для Фазы 1 в варианте B, но дешёвый и пригодится для presigned GET при показе записи позже.
- `multer` — сделать явной прямой зависимостью (сейчас только транзитивная через `@nestjs/platform-express`), раз код будет писать кастомный `StorageEngine` и импортировать его типы.
- `file-type` — проверка MIME по сигнатуре файла.
- `minio/minio` (docker image, не npm-пакет) — добавить сервис в корневой `docker-compose.yml`.
