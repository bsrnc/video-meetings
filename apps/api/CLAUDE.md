# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Run from this directory, or via root scripts (`dev:api`, `build:api`, `start:api`, `lint`, `lint:fix`, `typecheck`, prefixed at the repo root):

```bash
npm run dev           # nest start --watch
npm run build         # nest build
npm run start         # nest start
npm run start:prod    # node dist/main (after build)
npm run lint           # eslint
npm run lint:fix       # eslint --fix
npm run typecheck      # tsc --noEmit

npm run test           # jest (unit)
npm run test:watch
npm run test:cov
npm run test:e2e       # jest --config test/jest-e2e.json
```

To run a single test file: `npm run test -- app.controller.spec.ts` (path relative to `src/`, since Jest's `rootDir` is `src`).

Prisma CLI commands run from this directory (loads `prisma.config.ts` automatically):

```bash
npx prisma migrate dev --name <name>   # create + apply a migration
npx prisma generate                     # regenerate the client
```

`migrate dev` does **not** reliably regenerate the client in this Prisma 7 setup (observed: a new model was applied to the DB but missing from `@prisma/client` until `generate` ran explicitly) — always run `generate` after `migrate dev`, or after pulling schema changes from git.

## Architecture

Feature-module Nest app on top of Prisma/PostgreSQL:

- `src/main.ts` — bootstraps the app (`NestFactory.create`), enables CORS (`app.enableCors()`, open — no allowlist yet) so `apps/web` can call it cross-origin, applies a global `ValidationPipe` (`whitelist`, `forbidNonWhitelisted`, `transform`), raises the underlying Node HTTP server's `requestTimeout` to 30 minutes (Node's ~5 min default is too short for a 2 GiB meeting recording upload on a slow connection), listens on `process.env.PORT ?? 3000`. `apps/api/.env` sets `PORT=3001` since `apps/web` (Next.js) also defaults to 3000.
- `src/app.module.ts` — root module; imports `ConfigModule.forRoot({ isGlobal: true })`, `PrismaModule`, `UsersModule`, `AuthModule`, `MeetingsModule`.
- `src/prisma/` — `PrismaModule` (`@Global()`) provides `PrismaService`, a `PrismaClient` subclass wired with the `@prisma/adapter-pg` driver adapter (Prisma 7 requires an explicit adapter — no built-in engine) and hooked to Nest's `OnModuleInit`/`OnModuleDestroy` lifecycle.
- `src/users/` — `UsersService` (`findByEmail`, `create`) wraps `PrismaService.user`; not exported — the only consumers are this module's own CQRS handlers. `commands/create-user.command.ts` + `commands/handlers/create-user.handler.ts` (`CreateUserHandler`) creates a user. `queries/find-user-by-email.query.ts` + `queries/handlers/find-user-by-email.handler.ts` (`FindUserByEmailHandler`) looks one up by email. No controller.
- `src/auth/` — CQRS via `@nestjs/cqrs`. `AuthController` (`POST /auth/register` → 201, `POST /auth/login` → 200) only dispatches through `CommandBus`/`QueryBus`, no business logic. `commands/register.command.ts` + `commands/handlers/register.handler.ts` (`RegisterHandler`, `@CommandHandler`) creates the user — write side. `queries/login.query.ts` + `queries/handlers/login.handler.ts` (`LoginHandler`, `@QueryHandler`) looks the user up and verifies the password — read side, no mutation. Both handlers talk to `UsersModule` only through the CQRS bus (`FindUserByEmailQuery`, `CreateUserCommand` — defined in `src/users/`), never by injecting `UsersService` directly; `@nestjs/cqrs`'s `ExplorerService` wires handlers app-wide regardless of which module declares them, so `AuthModule` does not import `UsersModule`. Password hashing/verification (bcrypt) stays inline per handler — that's authentication logic, not user-data logic. Both handlers share `AuthTokenService` for JWT signing. `dto/register.dto.ts` / `dto/login.dto.ts` (`class-validator`) validate controller input before it becomes a command/query — register caps the password at 72 characters because bcrypt silently truncates past 72 bytes. `AuthModule` imports `CqrsModule` and registers handlers as providers (`CommandHandlers`/`QueryHandlers` arrays).
- `src/meetings/` — plain (non-CQRS) feature module, protected by auth. `MeetingsController` (`POST /meetings` → 201, `GET /meetings` → 200 list, `GET /meetings/:id` → 200 or 404, `POST /meetings/:id/recording` → 201) has `@UseGuards(JwtAuthGuard)` at the controller level. `MeetingsService` wraps `PrismaService.meeting` directly (`create`/`findAll`/`findOne`, throws `NotFoundException` in `findOne`). `dto/create-meeting.dto.ts` requires a non-empty `title`. Meetings have no owner/visibility scoping — `GET /meetings` returns all meetings for any authenticated user, not just the caller's own, and the recording upload endpoint is likewise open to any authenticated user, not just the meeting's creator. `MeetingsModule` imports `AuthModule` to get `JwtAuthGuard`, `StorageModule` for `StorageService`, and registers `MulterModule.register(createRecordingMulterOptions())` synchronously (no `ConfigService`/env dependency, so it's safe to evaluate at module-import time rather than needing `registerAsync`). See "File upload" below for the recording endpoint.
- `src/auth/guards/jwt-auth.guard.ts` — `JwtAuthGuard` (`CanActivate`), the shared auth guard for any protected route: reads `Authorization: Bearer <token>`, verifies it via `AuthTokenService.verify` (added alongside `sign`), throws `UnauthorizedException` if missing/invalid. Lives in `auth/` (not a separate `common/`/`shared/` module — only one guard exists so far); `AuthModule` exports both `AuthTokenService` and `JwtAuthGuard` for other feature modules to import.
- `src/meetings/guards/meeting-exists.guard.ts` — `MeetingExistsGuard` (`CanActivate`), applied only to `POST /meetings/:id/recording`. Guards run before interceptors in Nest's request lifecycle, so this 404s a nonexistent meeting id _before_ `FileInterceptor` reads and disk-writes the multipart body — without it, any authenticated user could force the server to fully receive up to the size limit against a made-up meeting id before getting a 404.
- `src/storage/` — `StorageModule` provides `StorageService`, a thin wrapper around `@aws-sdk/client-s3` (`S3Client`). Config (`STORAGE_ENDPOINT`/`STORAGE_REGION`/`STORAGE_BUCKET`/`STORAGE_ACCESS_KEY_ID`/`STORAGE_SECRET_ACCESS_KEY`/`STORAGE_FORCE_PATH_STYLE`, all via `ConfigService.getOrThrow`) resolves lazily on the first `upload()` call, not in the constructor — `StorageModule` is transitively imported by `AppModule` (via `MeetingsModule`), so eager resolution would make every app bootstrap require `STORAGE_*`, including `auth`/`meetings` e2e specs that never touch storage. `upload(key, body: Readable, contentType)` streams via `@aws-sdk/lib-storage`'s `Upload` (S3 multipart upload, no in-memory buffering of the whole object). Implements `OnModuleDestroy` to call `S3Client.destroy()` and release its HTTP agent/sockets. Not `@Global()` — imported by feature modules that need it (`MeetingsModule`).
- `prisma/schema.prisma` — `User` model (`id`, `email` unique, `passwordHash`, `createdAt`) and `Meeting` model (`id`, `title`, `createdAt`, `recordingKey`, `recordingStatus` — `RecordingStatus` enum `UPLOADING`/`READY`/`ERROR`, nullable until an upload starts, `recordingError`); `prisma/migrations/` holds applied migrations.
- `prisma.config.ts` — Prisma 7 config (replaces the old `datasource.url` in the schema file); loads `.env` itself via `import 'dotenv/config'` since the Prisma CLI does not auto-load it.
- `test/auth.e2e-spec.ts` — e2e coverage for register/login (success, duplicate email, wrong/missing credentials).
- `test/meetings.e2e-spec.ts` — e2e coverage for create/list/get-by-id, including 404-not-found and the auth guard (missing token and invalid token) on every route.
- `test/meetings-recording.e2e-spec.ts` — e2e coverage for `POST /meetings/:id/recording` against the real MinIO/Postgres from `docker-compose.yml`: valid upload → `READY` + `recordingKey`; a later rejected re-upload attempt leaves the existing `READY` recording's `recordingKey` untouched; any authenticated user (not just the creator) can upload; a file rejected by the coarse declared-Content-Type filter (415) and one that passes that filter but fails the magic-byte check (415, spoofed `Content-Type: video/mp4` on non-mp4 bytes) are both covered separately, neither leaves the meeting `READY`; 404 for a missing meeting; 401 unauthenticated. Doesn't send an actual oversized file to prove the 2 GiB limit end-to-end (impractical in a fast test) — that half of "invalid type/size rejected" is covered by unit tests instead (`recording-multer.options.spec.ts` proves `limits.fileSize` wiring, `multer-exception.filter.spec.ts` proves the 413 mapping).
- Both e2e spec files build their own `INestApplication` with the same global `ValidationPipe` as `main.ts` (test app bootstrapping doesn't go through `main.ts`, so the pipe is duplicated in each spec's `beforeEach`).
- `test/` — e2e tests (`jest-e2e.json` config), separate from unit tests colocated in `src/*.spec.ts`.

**Database**: PostgreSQL via the root `docker-compose.yml` (`localhost:5434`, see root `CLAUDE.md`). **Object storage**: MinIO (S3-compatible) via the same root `docker-compose.yml` — `minio` service (API on `9000`, console on `9001`) plus a `minio-init` one-shot container that creates the recordings bucket via `mc mb --ignore-existing` on startup. `apps/api/.env` (gitignored; see `.env.example`) holds `DATABASE_URL`, `JWT_SECRET`, and `STORAGE_*` (endpoint/region/bucket/credentials/`STORAGE_FORCE_PATH_STYLE`) — all required, no defaults, `ConfigService.getOrThrow` fails fast if missing. `STORAGE_*` is checked lazily (see `StorageService` below), not at boot — a checkout missing `STORAGE_*` still boots and passes `auth`/`meetings` tests, only failing on the first actual `POST /meetings/:id/recording`.

Prettier (`.prettierrc`) and ESLint (`eslint.config.mjs`) configs are the Nest generator's defaults; the Prettier values match the repo-root `.prettierrc.json`.

## File upload

Architecture background/rationale: @docs/research-meeting-upload.md. Phase 1 implementation, as built:

- `POST /meetings/:id/recording`, `multipart/form-data` field `file`. `MeetingExistsGuard` 404s a missing meeting _before_ the body is read (see above); 401/invalid-token like every other `meetings` route (open to any authenticated user, not scoped to the meeting's creator).
- `src/meetings/recording-upload.constants.ts` — the fixed decisions from research's open questions: `RECORDING_MAX_FILE_SIZE_BYTES` (2 GiB) and `ALLOWED_RECORDING_MIME_TYPES`. That allowlist holds the MIME strings `file-type`'s magic-byte detector actually returns for our installed version (e.g. `audio/vnd.wave` for WAV, `audio/x-m4a` for M4A) — not the conventional client-declared strings — since the detector's output is the authoritative check.
- `src/meetings/recording-multer.options.ts` (`createRecordingMulterOptions`) — `multer.diskStorage()` to `os.tmpdir()` (a temp file, not full in-memory buffering — the research-recommended fully-streaming custom `StorageEngine` was judged more complexity than Phase 1 warrants; disk is the research doc's sanctioned fallback), `limits.fileSize`, and a cheap `fileFilter` that rejects a declared Content-Type outside `video/*`/`audio/*`/`application/octet-stream` (declared type is spoofable or generic, so this is a coarse pre-filter to save I/O on obvious junk — a client that declares `application/octet-stream` for an unrecognized extension still reaches the authoritative magic-byte check instead of being rejected here).
- `src/meetings/meetings.service.ts` (`uploadRecording`) — detects the real type via `file-type`'s `fromFile` against the tmp file's magic bytes _before_ touching `recordingStatus`/`recordingKey` at all (rejects with `UnsupportedMediaTypeException` if not in the allowlist, leaving any existing recording's state exactly as it was — a rejected re-upload must not erase a still-valid stored recording); only once validation passes does it set `recordingStatus = UPLOADING` and stream the tmp file to storage at the deterministic key `meetings/{meetingId}/recording` via `StorageService.upload` (re-upload overwrites, matching the plan's "retry after a rejected upload" scenario), then `recordingStatus = READY` + `recordingKey`. A genuine failure past that point sets `recordingStatus = ERROR` + `recordingError` before rethrowing (a type-rejection does not — it rethrows immediately, per the above); if that status write itself fails, it's logged (`Logger`) rather than silently swallowed. `uploadRecording` runs each call through a per-meeting-id promise chain (`runExclusive`) so two concurrent uploads to the same meeting can't interleave their storage write / DB update in a way that leaves `recordingStatus`/`recordingKey` describing neither attempt; different meetings never block each other. The tmp file is always deleted (`finally`).
- `src/meetings/multer-exception.filter.ts` (`MulterExceptionFilter`, `@UseFilters` on the route) — catches `PayloadTooLargeException`, not `MulterError`: `@nestjs/platform-express`'s `FileInterceptor` already converts multer's raw `LIMIT_FILE_SIZE` `MulterError` into a `PayloadTooLargeException` internally (`multer.utils.js`'s `transformException`) before it can ever reach a Nest exception filter, so `@Catch(MulterError)` would never fire. This filter exists purely to replace multer's raw English message with a clear one.
- `file-type` is pinned to exact `16.5.4` in `package.json` (no `^`), not latest — later majors are ESM-only and Jest's CJS test VM can't `import()` them without `--experimental-vm-modules` (confirmed by hitting `ERR_VM_DYNAMIC_IMPORT_CALLBACK_MISSING_FLAG` under `test:e2e` with a dynamic import of the current major). `16.5.4` is the last version with a CommonJS build and a plain static import, at the cost of the older `fromFile`/`fromBuffer` API (not `fileTypeFromFile`/`fileTypeFromBuffer`, which only exist from v17 on).
